# SISF 阶段推进与收口

## 主计划是 todo.md

- `todo.md` 是设计文档的执行拆解：T1–T12 对应 12 个阶段，**每条子任务后附最小可证明判据**
  （通常是具体单测名或具体命令 + 具体数字）。开工前先读该阶段全部子任务与依赖链
  （T1→T2→T3→T4→{T5,T7}；T5→T6；{T5,T7}→T8；T2→T9；{T6,T8,T9}→T10→T11→T12）。
- 勾选约定：`[ ]` 待办 · `[x]` 已完成。**每阶段末尾的"验收（整段）"通过才提交一次**——
  阶段内不碎片提交。
- 整段验收用 `sisf-gates` skill 的闸门集合，证据是原命令实跑的真实数字。

## 验收证据怎么写

写进 todo.md 对应行，要求可被下一条会话照抄复现：

- 命令原文 + 真实计数（"58 绿 0 warning（asset 16 + media 8 + …）"这种带分解的形式）。
- 手测项写明看了什么、读到什么（fps、帧号、断言行）。没做到的用 ⚠️ 或直接留 `[ ]`，
  **不要把"未验证"写成"已完成"**；被环境挡住的（如需肉眼开一次 WebGPU 页面）登记为待办而不是打勾。

## 实现期发现的事实

- 每条与本仓库文档/设计不符的事实，追加到该阶段的
  "### T\<n\> 期间发现并修正的事实（供后续阶段引用）" 编号列表——后续阶段会引用它们。
- 历史条目**不回改**：发现旧证据计数错了（如 T4 那行漏计 `sisf-app` 6 项），在后续阶段的
  清单里点名修正。
- 涉及某平台的长期行为，同步进 `docs/` 对应文档（android/audio/input/platforms/…）。

## 提交

- 一次阶段验收 = 一次提交。信息格式沿用 git log 惯例：
  `P<编号> <主题>: T<阶段> <一句话> —— <为什么这么做>`（中文，破折号后是动机不是复述）。
- **不要主动 push**。历史上大量提交停在本地（`未 push`），push 需要用户明确许可。
- 提交前 `git status` 检查暂存内容；`target/`、`web/pkg/` 产物按现有 `.gitignore` 处理，
  发现可疑的大文件或疑似密钥文件先停下来核对。

## 收尾

- 阶段收口后更新项目记忆中该阶段的状态文件（已完成/未达成/待复验三态要区分清楚，
  复验没做过就打 ⚠️）。
- 未达成项（CI 腿、真机手测等）在提交信息与 todo.md 里如实留痕，让下一条会话能接手。
